Testing

A documentation of the multiple testing approaches at different scales we have conducted throughout the project development cycle.

Python Unit Testing

Unit tests for the Python backend were run using Pytest. There are a total of 94 test cases, which all pass with a coverage of 93%.

The tests use the standard workflow for unit tests, mocking external dependencies as needed using unittest.mock and unittest.patch. This is an example of a test case for the Model.generate function, which mocks the API call to the LLM and checks that the function correctly processes the response and returns the expected output. 

# Backend-Test\test_agents.py

@patch('requests.request')
def test_generate_success(self, mock_request):
	"""Test successful model generation"""
	mock_response = Mock()
	mock_response.status_code = 200
	mock_response.json.return_value = {"choices": [{"message": {"content": "Test response"}}]}
	mock_request.return_value = mock_response

	model = Model(url="http://test.com", model="test-model")
	messages = [{"role": "user", "content": "Hello"}]
	
	result = model.generate(messages, temperature=0.3)
	
	assert result.json() == mock_response.json()
	mock_request.assert_called_once()
C# Unit and Integration Testing

Unit tests for the C# was run using dotnet build

The C# test suite is driven by a custom PowerShell orchestration script (run-tests.ps1) using xUnit and the .NET 10 CLI. To achieve high-fidelity results on both native PCs and Mac VMs (ARM64), the pipeline dynamically resolves and injects the required Windows App Runtime native binaries into the test environment.

For integration tests which was included in unit tests, we utilize a combination of In-Memory Databases, Dependency Injection mocking, and Mocked HTTP Handlers to ensure tests are fast, isolated, and representative of real-world scenarios. This example demonstrates how we test the QuestionnaireAPIService by mocking the HttpClient. Instead of making a real network call, we intercept the request and force a "Success" (OK) or "Failure" (BadRequest) status to ensure our service handles remote API responses correctly.

// AvatarFormsApp.Tests/Services/QuestionnaireAPIServiceTests.cs

[Fact]
public async Task SendQuestionnaireAsync_ReturnsTrue_WhenPostSucceeds()
{
    // Arrange: Create a mock Questionnaire model
    var q = new Questionnaire { Name = "Test", Id = "id-123", Questions = new() };
    _mockService.Setup(s => s.GetWithQuestionsAsync("id-123"))
        .ReturnsAsync(q);

    // Mock the HTTP layer to return a "200 OK" status
    var client = CreateMockClient(HttpStatusCode.OK);
    var sut = new QuestionnaireAPIService(_mockService.Object, client);

    // Act: Attempt to send the questionnaire to the remote endpoint
    var result = await sut.SendQuestionnaireAsync("id-123", 8882);

    // Assert: Verify the service correctly interpreted the success
    Assert.True(result);
}
DeepEval Testing

Testing of our AI agents was conducted using the DeepEval framework, which allows for automated evaluation of LLM outputs using an LLM as a judge. Each agent was evaluated on a set of 25 test cases covering various conversational scenarios, and both open-ended and multiple-choice question types, then scored against 2 metrics:

  • Talker Agent - Answer Relevance (asking the right question) and Question Appropriateness (phrasing the question appropriately).
  • Evaluator Agent - Satisfactory Judgement Accuracy and Skip Decision Accuracy (correctly determining if the user's response is satisfactory or if the question should be skipped).
  • RAG Agent - Answer Relevancy (retrieving the right information) and Faithfulness (retrieving information that is factually correct and supported by the conversation).

Test Cases Summary

Compatibility Testing

Compatibility testing was conducted on a range of Windows-based systems using both NVIDIA and AMD GPUs, alongside machines equipped with AMD and Intel CPUs. Theoretically, the application can be run on any devices with a CPU architecture of either AMD64 (AMD CPUs circa 2003+) or ARM64 (Intel CPUs circa 2006+), while compatibility with Qualcomm Snapdragon CPUs have not yet been tested.

The Text-To-Speech and 3D avatar lip-sync models are already deployed using the ONNX Runtime format, but the LLM solution (.llamafile) has limited documentation on NPU support. That being said, the application ran reliably across these configurations when GPU acceleration was available. However, when running on CPU-only systems, particularly during LLM inference, performance degraded significantly as expected, which will be discussed further in the Performance section.

As this is a Windows-based application, compatibility with macOS or other UNIX-based systems was not tested.

Performance Testing

The performance was tested on devices with the following system specifications:

  • CPU-Only Windows System: AMD Ryzen 5 4600H (Mobile) (6 Cores) + 16GB RAM
  • CPU + GPU (Mid-Range with 6GB VRAM) Windows System: Intel i5-9600KF (6 Cores) + NVIDIA RTX 2070 6GB + 32GB RAM
  • CPU + GPU (Mid-Range with 12GB VRAM) Windows System: AMD Ryzen 5 5700X (8 Cores) + NVIDIA RTX 4070Ti 12GB + 32GB RAM

We settled for these three control systems as we believe these are realistic representations of what lower-end, mid-range, and high-end devices would look like respectively for our client demographics. The majority of our clients at NAS schools may be able to get access of a shared school device with GPU specifications between the control that we have chosen. We have also included another control device with no GPU to highlight the impracticality of running this application at its current state fully on CPU inferencing.

The performance results clearly demonstrate that GPU acceleration is essential for practical use of the system. While the Talker agent performs reasonably even on CPU-only hardware (4.58s), the Evaluator agent introduces a significant bottleneck, with nearly 49 seconds of delay, resulting in an overall response time exceeding 53 seconds. This makes the application unsuitable for real-time conversations when running purely on CPU.

In contrast, both GPU equipped systems show a dramatic improvement in performance, reducing total response time to under 10 seconds. Even the mid-range GPU setup (RTX 2070) achieves a nearly 6x speedup, while the higher-end RTX 4070Ti provides further, albeit smaller, gains. This suggests that most of the performance benefit comes from having a GPU at all, with diminishing returns at higher tiers.

It is also important to note that these benchmarks were recorded within a testing framework, meaning real-world application runtimes are approximately 20% faster due to the absence of testing overhead. Additionally, the context size is dynamically adjusted at runtime, particularly for the RTX 2070 with its 6GB of VRAM, allowing the system to maintain comparable performance to any higher-end GPUs by reducing memory usage. This optimisation introduces only minor inaccuracies, but ensures consistent responsiveness across a wider range of hardware.

Round 1 - Project Showcase

On 27th February 2026 and 3rd March 2026, we presented at both NTTDATA and the UCL Student Showcase, where company executives and those interested in the application for AI in EdTech and SEND came and tested our products. We managed to test with teachers, NHS workers and technology experts, getting very useful feedback for our final few adjustments and potential future expansions with our product. Here are some of our photos during the events.

We received many positive feedback from the experts with the following to name a few:

  • Having raw interview response output included which may contain useful data for NAS schools to process.
  • Including support for multiple languages which may be useful in the NHS.

Here, we also received feedback that our product may be able to be used for interactive surveys in museums and fairs, with a big screen and a kiosk to answer trivias or any similar activities. This was a great feedback, as we realised that the applications for this technology are not confined to what we've defined in our initial requirements.

Round 2 - Simulated Testing

Towards the end of the project development cycle, we continued to test and obtain feedback from our fellow colleagues from a variety of fields to gain their unique insight on the applications and usability of our solution. Across 14 registered testers, we managed to receive a rating of 3.93 stars over 5 stars for overall usability.

Amongst the usability metrics, we've managed to get generally positive feedback for all the metrics except performance, as expected as the conversations were 2-3x slower than real-time conversation. The majority of them agreed that they would definitely use the application again if this problem is solved, while some also included feedback on the size of UI elements hindering visibility.

Now for the feature completeness metrics, we got very good feedback across the coherence & quality and avatar choice metrics, with mixed feedbacks on comfort. Testers remarked that having custom avatars pulled them in to the interview and the coherence made the experience fairly pleasant. However, realism and animations needed improvement as we've discovered that the animation seems clunky and unnatural, while inclusivity was not received well either as there were no variety of avatar demographics and multilingual support during the majority of the time of testing.

Taking into note the feedback that we've received, in addition to discussion with our client, we have implemented several small quality-of-life improvements:

  • The UI elements now scale with Windows font size so that it can be set to preference.
  • Avatars can now be added by the users, instead of just the developers with a simple file select.
  • Multilingual speech recognition is now supported by the AI agents to allow non-English input for inclusivity.

Further improvements like having more realistic avatars and animations using Unreal Engine's Metahumans and faster LLM inference have not been yet implemented, but will be discussed further in the Future Work section.
