Design Patterns

We maintained high code readability and maintainability by following several proven software design patterns.

Pattern Implementation
Dependency Injection We utilised this pattern in the WinUI frontend (C#). This can be seen through the usage of App.GetService<T>() to provide services like IPythonProcessService, ILlamafileProcessService, and ILocalSettingsService, decoupling the UI from backend implementations.
Observer We utilised this pattern heavily to communicate state changes across the different systems in our software. For instance, _pythonProcessService.OutputReceived += _onPythonOutput routes standard output streams from the Python backend directly to the WinUI DispatcherQueue to update the console log in AvatarPage.
Facade We implemented the Python class AvatarFormsInterviewer, which hides the complexities of multiple agentic LLM logic. It encapsulates the underlying initialisations of TalkerAgent, EvaluatorAgent, and RAG_Agent, providing a streamlined interview loop.
Strategy We implemented distinct agent classes (TalkerAgent, EvaluatorAgent, RAG_Agent) in the Python backend to encapsulate the specific reasoning strategy needed at different stages of the interview (e.g: asking standard queries vs evaluating an off-topic user response).
State Our AvatarFormsInterviewer functions as a conversation state machine. It actively transitions between states (questions_index, last_evaluation, and cutoff counters), deciding dynamically whether to prompt for more information or smoothly advance the interview.
Design Principles
  • Single Responsibility Principle (SRP): Each component has a strictly defined responsibility. In the Agent Orchestration Layer (Python), the TalkerAgent drafts speech, the EvaluatorAgent analyses response accuracy, and the RAG_Agent extracts structured final answers. In the .NET application, AvatarPage.xaml.cs only handles view and peripheral logic, delegating heavy logic to APIs and services
  • Separation of Concerns (SoC): There is a clear boundary between UI layout (WinUI), backend logic (.NET), agent orchestration (Python) and avatar generation (HeadTTS). Instead of mixing all the separate logics in the main .NET application, the systems interact through APIs such as WebSockets and lightweight HTTP servers.
  • Open/Closed Principle (OCP): .NET functionalities are defined through clear interfaces such as ILocalSettingsService and IPythonProcessService. The system can swap how Python processes are started or how settings are cached without modifying logic in AvatarPage.
  • Don't Repeat Yourself (DRY): Repetitive logic is consistently abstracted into reusable functions and methods, significantly reducing redundancy across the system.
