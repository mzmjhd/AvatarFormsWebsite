Implementation

A deep dive into the technical details of the project.

Agent Orchestration Overview

The application uses a custom Agent Orchestration layer centred around the AvatarFormsInterviewer class. This class coordinates the interview, maintaining the state of the conversation and deciding when to transition between questions based on agent feedback, whilst Agent and Model classes interface with the LLM. The framework is designed to be modular and model agnostic, to allow for Agents to be easily modified or switched out when needed.

AvatarFormsInterviewer

The AvatarFormsInterviewer class is the central orchestration layer for the interview flow. It maintains conversation state, coordinates the Talker, Evaluator and RAG agents, decides when to advance between questions, and collects final answers for downstream processing.

Key responsibilities:

  • Track questions, conversation history and other metadata so all agents share a consistent view of the interview state.
  • Use the EvaluatorAgent to decide whether a user's response is satisfactory or if follow-up is required, and apply a configurable cutoff to avoid getting stuck on a single question.
  • Delegate generation to the TalkerAgent for question phrasing and follow-ups, and to the RAG_Agent when building final, structured answers (including MCQ matching).
  • Optionally log agent prompts and outputs via a Tracer for debugging and observability purposes.

Representative excerpt from main.py showing the main methods:

class AvatarFormsInterviewer:
    def __init__(self, is_local: bool = False, model_name: str = None, local_port: int = 8081, cutoff: int = 4, log_dir: str = None, print_logs: bool = False) -> None:
        self.cutoff = cutoff
        self.user_role = "user"
        self.AI_role = "assistant"
        self.is_local = is_local
        self.model_name = model_name
        self.tracer = Tracer(log_dir=log_dir, print_logs=print_logs) if log_dir else None

    def build_interview(self, questions: list[dict], interview_context: str) -> None:
        self.questions = questions
        self.interview_context = interview_context
        self.questions_index = 0
        self.conversation_history = []
        self.question_labels = []
        self.answers = [""] * len(self.questions)
        self.model = self.get_model()
        self.talker = TalkerAgent(model=self.model, conversation_history=self.conversation_history, interview_context=self.interview_context, tracer=self.tracer)
        self.evaluator = EvaluatorAgent(model=self.model, interview_context=self.interview_context, tracer=self.tracer)
        self.rag_agent = RAG_Agent(model=self.model, interview_context=self.interview_context, tracer=self.tracer)

    def start_interview(self) -> str:
        self.reset_interview()
        question = format_question(self.questions[self.questions_index])
        speech = self.talker.ask_question(question, previous_q_and_a=None)
        self.conversation_history.append({"role": self.AI_role, "content": speech})
        self.question_labels.append(self.questions_index)
        return speech

    def respond(self, response: str) -> tuple[str, bool]:
        self.conversation_history.append({"role": self.user_role, "content": response})
        evaluation = self.evaluator.evaluate(format_question(self.questions[self.questions_index]), self.get_conversation_section(self.questions_index))
        if self.should_cutoff() or evaluation["satisfactory"] or evaluation["override_skip"]:
            self.questions_index += 1
            self.answers[self.questions_index-1] = self.collect_answer(self.questions_index-1)
        if self.questions_index < len(self.questions):
            # either a new main question or a follow-up depending on last evaluation
            next_q = format_question(self.questions[self.questions_index])
            q_and_as = self.collect_all_answers()
            q_and_as = None if all(a == "" for a in q_and_as.values()) else q_and_as
            speech = self.talker.ask_question(next_q, previous_q_and_a=q_and_as)
            self.conversation_history.append({"role": self.AI_role, "content": speech})
            self.question_labels.append(self.questions_index)
            return speech, True
        else:
            closing = self.talker.closing_statement()
            self.conversation_history.append({"role": self.AI_role, "content": closing})
            return closing, False
Model Class

The Model class serves as a standardized interface for interacting with an LLM endpoint. All agents make use of this class, so the interviewer can be modified to use a different LLM, whether local or cloud-based, purely by modifying the Model initialisation.

# agents.py

class Model:
    def __init__(self, url: str, model: str, api_key: str = None, params: dict = None) -> None:
        self.url = url
        self.model = model
        self.api_key = api_key
        self.params = params if params is not None else {
            "max_tokens": 4096,
            "top_p": 1,
            "top_k": 40,
            "presence_penalty": 0,
            "frequency_penalty": 0,
            "temperature": 0.6,
            "stream": False
        }
        
    def generate(self, messages: list, temperature: float = None) -> dict:
        # Call the model's API with the messages and return the response
        payload = {
            "model": self.model,
            **self.params,
            "messages": messages
        }
        if temperature is not None:
            payload["temperature"] = temperature
            
        headers = {
            "Accept": "application/json",
            "Content-Type": "application/json",
        }

        if self.api_key:
            headers["Authorization"] = f"Bearer {self.api_key}"
        response = requests.request("POST", self.url, headers=headers, data=json.dumps(payload))

        if response.status_code == 200:
            return response
        else:
            raise Exception(f"API call failed with status code {response.status_code}: {response.text}")
Agent Classes

The Agent classes act as intermediaries between the AvatarFormsInterviewer and the Model, taking in structured data to be formatted into text prompts and passed into Model.generate. The Agent then cleans and formats the output to be returned to the AvatarFormsInterviewer. The base class Agent is inherited by all other Agents. An optional Tracer object can be passed to log all calls made with the Agent as described in a section below.

# agents.py

class Agent:
    def __init__(self, model: Model, tracer: Tracer = None) -> None:
        self.agent = self.__class__.__name__
        self.model = model
        self.tracer = tracer

    def run(self, messages: list, temperature: float = None) -> str:
        response = self.model.generate(messages, temperature=temperature)
        output = response.json()["choices"][0]["message"]["content"]
        if self.tracer:
            self.tracer.log(
                agent_name=self.agent,
                prompt=messages,
                output=output,
                temperature=temperature,
                response_time=response.elapsed.total_seconds()
            )
        return output

class EvaluatorAgent(Agent):
    def __init__(self, model: Model, interview_context: str, tracer: Tracer = None, language: str = "en-US") -> None:
        super().__init__(model, tracer=tracer)
        self.prompt = Evaluator_system_prompt
        self.interview_context = interview_context
        self.language = language

    def evaluate(self, question: str, conversation_history: list) -> dict:
        transcript = conversationToText(conversation_history)
        system = self.prompt(self.interview_context, question, transcript, self.language)
        messages = [{"role": "system", "content": system}]
        output = self.run(messages, temperature=0.2)
        return outputToJSON(output)

Formatting Utilities

To format data for use in prompts, the Agents use utility functions in formatting.py.

Name Function
clean_script Sanitises LLM output by removing content within XML tags , emojis and text within brackets.
LLM_strip Removes XML-style tags (e.g., `<think>...</think>`) and all content contained within those tags. Is run as part of clean_script.
conversationToText Converts a list of message dictionaries into a single, newline-separated string.
format_q_and_as Transforms a dictionary of question-answer pairs into a readable string using "Q:" and "A:" prefixes for each entry.
format_question Formats a question dict into a string. For multiple-choice questions, appends the options.

LLM_strip uses regular expressions to identify and remove XML tags:

# formatting.py

def LLM_strip(text: str) -> str:

    tags = re.findall(r"<[^>/]*>", text, flags=re.DOTALL)

    for tag in tags:

        pattern = re.escape(tag) + r".*?" + re.escape(tag.replace("<", "</"))

        text = re.sub(pattern, "", text, flags=re.DOTALL)

    return text.strip()

WinUI 3 Architecture

The frontend is built with WinUI 3 and C#, using a modular page-and-component structure that keeps presentation and behavior predictable across dashboard, response, and avatar workflows. Reusable user controls are used for repeated UI patterns so interaction behavior remains consistent while reducing duplicated implementation effort.

A key implementation goal was to preserve the default Microsoft look and feel by relying on the standard WinUI control library and design language wherever possible, with only minimal visual overrides. This keeps the interface aligned with the wider Microsoft ecosystem and makes interactions immediately familiar for Windows users.

This architecture also aligns well with the broader MVVM-oriented application design. View composition stays lightweight, while state and command handling are maintained in dedicated ViewModels and services, enabling clearer debugging, easier extension, and lower risk when iterating on the interface.

Mica + Frosted Surface System

The frontend visual language follows a frosted-mica direction where layered translucent surfaces separate context without introducing visual clutter. Primary containers establish depth with subtle blur and low-contrast boundaries, while content cards remain slightly more opaque to preserve readability and reduce background interference.

Surface hierarchy is intentionally restrained: one backdrop layer for global atmosphere, one panel layer for navigation and context, and one content layer for task execution. This keeps the UI calm and legible while still communicating spatial structure through soft elevation and tonal separation.

Dark Mode Implementation

Dark mode is implemented as a first-class design mode rather than a post-process color inversion. Tokens define background, surface, border, muted text, and accent behavior so that component styling can switch coherently while preserving information hierarchy and semantic emphasis.

For a low-stimulation environment, contrast is calibrated to avoid harsh luminance jumps: body copy remains readable, secondary text is softened but still accessible, and accent gradients are used selectively for section headers and key affordances. This maintains focus over long sessions without visual fatigue.

Typography + Spacing System

Typography uses clear role separation between heading, body, and muted-support text so users can scan dense technical content quickly. Section titles use stronger weight and gradient emphasis, while paragraphs and supporting labels follow stable line-height and spacing rules to keep reading flow smooth.

Spacing follows a consistent rhythm across cards, list groups, and code-adjacent explanation blocks. Predictable vertical gaps improve chunking and lower cognitive overhead, especially when users move between implementation categories that contain mixed prose and technical detail.

Interaction + Motion

Interaction behavior is designed to feel responsive but restrained. Hover, focus, and state transitions use short-duration easing to communicate affordance changes without drawing unnecessary attention away from task content.

Motion is deliberately subtle and functional: tab switching clarifies context changes, card emphasis supports discoverability, and control feedback confirms user actions. This avoids high-arousal animation patterns while still providing clear interaction cues for confidence and flow continuity.

Component Consistency

Consistency is enforced through shared component patterns for cards, tabs, navigation regions, links, and typography roles. Reusing established structures reduces relearning cost and ensures users can transfer interaction expectations between pages with minimal friction.

At implementation level, standardized visual tokens (radius, border, shadow, surface tone, and gradient accent) keep components visually coherent in both light and dark modes. The component set also stays close to default Microsoft control behaviors so the product remains in sync with Microsoft platform conventions while preserving a unified frontend identity.

Accessibility + Comfort

Accessibility and comfort are treated as implementation constraints, not optional enhancements. Keyboard-reachable controls, visible focus states, and clear text hierarchy support practical usability across different interaction preferences and attention profiles.

The low-stimulation objective is reflected in reduced visual noise, moderated contrast transitions, and predictable layout behavior. Together, these choices improve long-duration usability and reduce cognitive strain while preserving clarity for critical actions.

System Overview

Our backend implementation is built on .NET 10 using the Model-View-ViewModel (MVVM) architecture with supporting Services and follows best practices for scalability, maintainability, and security.

Core business logic are broken down into smaller components based on their functionalities, allowing for reusability and clear separation of concern. Core services for our backend implementation include:

  • FormsLinkParserService: Employs a web scraper with a C# script to intelligently collect questionnaire details and metadata.
  • PythonProcessService: Manages the Python runtime application initialisations and startup arguments.
  • LlamafileProcessService: Manages the Llamafile (LLM) server startup with dynamic resource allocation.
  • QuestionnaireAPIService & ResponseAPIService: Manages API connection for questionnaire and response data pipeline.
  • ResponsesPageViewModel & ResponseDetailPageViewModel: Collects data from the database and export them using a CSV format to ease form response data processing.
Forms Parsing

To allow educators and users to easily import existing questionnaires without manual data entry, we implemented the FormLinkParserService. This service uses a hidden WebView2 control to programmatically navigate to form URLs and extract the underlying question metadata into a unified ParsedQuestion format. It handles the two most common platforms using fundamentally different strategies:

Microsoft Forms dynamically loads its data. Rather than scraping the DOM, the service hooks into the WebView's WebResourceResponseReceived event to intercept the raw network traffic. It listens for specific API endpoints (like runtimeFormsWithResponses or ResponsePageStartup.ashx) and captures the JSON payload directly from the stream.

Additionally, because some forms are hidden behind a landing page, the service automatically injects JavaScript to simulate a click on "Start" buttons to trigger the network request.

async void OnResponseReceived(object? sender, CoreWebView2WebResourceResponseReceivedEventArgs e)
        {
            if (tcs.Task.IsCompleted) return;

            var uri = e.Request.Uri;

            // Accept the known MS Forms API endpoints.
            // ResponsePageStartup.ashx is also included — WebView2 (unlike Playwright's
            // fresh headless browser) reuses Edge's cache/session, so after clicking Start
            // the questions are already in memory and no new runtimeFormsWithResponses
            // request fires. The data comes from the initial ResponsePageStartup.ashx instead.
            bool isFormApi = uri.Contains("runtimeFormsWithResponses") ||
                             uri.Contains("light/forms") ||
                             uri.Contains("formapi/api") ||
                             uri.Contains("ResponsePageStartup.ashx");

            if (!isFormApi) return;

            Log($"Checking API response from: {uri}");

            try
            {
                var irasStream = await e.Response.GetContentAsync();
                using var reader = new System.IO.StreamReader(irasStream.AsStreamForRead());
                var text = await reader.ReadToEndAsync();

                if (!text.Contains("\"questions\":["))
                {
                    Log("Response missing questions array, skipping.");
                    return;
                }

                Log($"Found form payload ({text.Length} chars) from: {uri}");
                var node = JsonNode.Parse(text);
                Log("JsonNode parsed OK.");

                // ── Full JSON dump ──────────────────────────────────────────
                Log("=== RAW JSON START ===");
                Log(node!.ToJsonString(new System.Text.Json.JsonSerializerOptions { WriteIndented = true }));
                Log("=== RAW JSON END ===");

                tcs.TrySetResult(node);
            }
            catch (Exception ex)
            {
                Log($"Response handler EXCEPTION: {ex.GetType().Name}: {ex.Message}");
                // Don't fail the TCS — keep waiting for another response
            }
        }

Unlike Microsoft, Google Forms embeds its entire question structure into the HTML upon initial load inside a global JavaScript array. The service navigates to the URL, waits for the page to load, and then uses ExecuteScriptAsync to extract and stringify the window.FB_PUBLIC_LOAD_DATA_ variable.


    // Helper to crawl the JSON tree and find all arrays
    private void FindAllArrays(JsonNode? node, List found)
    {
        if (node is JsonArray arr)
        {
            found.Add(arr);

Once the raw JSON (from either platform) is captured, custom parsing algorithms crawl the JSON nodes to extract form titles, descriptions, question types, and multiple-choice options. Regex is used via a CleanHtml helper to strip out unwanted formatting tags, ensuring the resulting data is pristine before being saved to the local SQLite database.

Llamafile Process Service

The LlamafileProcessService is the main service managing the LLM server. For our use case, we opted for packaging our LLM into an executable using Llamafile, an open source solution to distribute LLMs as a single file, to simplify the user experience. This allows users with minor technical knowledge to run the application without any additional setup, removing the need to install additional third-party local LLM server providers.

It is symmetrical to PythonProcessService, where it starts the Llamafile process with the right parameters (port, GPU/CPU flags, model-specific args), stream logs to the in‑app console log in AvatarPage, and provides structured API methods to manage the process lifecycle: start, restart, and clean shutdown on exit - especially important to prevent any idle resource usage.

Before running the process, we implemented a method to get the user's machine hardware information, private (string type, long mem) GetGpuInfo(), to allow the LLM to be initialised with the best parameters and context size with stability based on the machine's specifications. Machines with insufficient video memory (VRAM) will be defaulted to do CPU inferencing, as llamafiles will fail to run when experiencing memory constraint.

var (gpuName, gpuMem) = GetGpuInfo();
System.Diagnostics.Debug.WriteLine($"Detected GPU: {gpuName} with {gpuMem} MB VRAM");
var gpuArgs = 0; // Default to CPU
var contextArgs = 1024; // Default to 1K context window for CPU
if (gpuName.Contains("NVIDIA", StringComparison.OrdinalIgnoreCase)
    || gpuName.Contains("AMD", StringComparison.OrdinalIgnoreCase)) // Only supports NVIDIA and AMD GPUs
{
    if (gpuMem > 6144) // 6GB+ VRAM
    {
        gpuArgs = 9999;
        contextArgs = 4096;
    }
    else if (gpuMem > 4096) // 4GB+ VRAM
    {
        gpuArgs = 9999;
        contextArgs = 2048;
    }
}
else
{

Response Export

To make the collected interview data actionable, the application implements a native data export pipeline that transforms relational database records into flat, universally compatible CSV files. This allows educators and administrators to easily import the data into external tools like Excel or pandas for further analysis.

The export mechanism leverages the native Windows.Storage.Pickers.FileSavePicker to handle file system interactions safely, and supports two distinct export modes: extracting a single interview session, or aggregating all responses for a given questionnaire into a bulk report.

Exporting a single session is straightforward, but bulk exporting requires transforming the hierarchical data (Questionnaires -> Sessions -> Responses) into a flat, tabular format. Because users might skip questions or encounter dynamic interview flows, the export logic dynamically maps and aligns responses to their corresponding question columns using LINQ.

// 1. Get all unique questions across all sessions to establish consistent columns
var questions = sessions
    .SelectMany(s => s.Responses)
    .Where(r => r.Question != null)
    .Select(r => r.Question!)
    .GroupBy(q => q.Id)
    .Select(g => g.First())
    .OrderBy(q => q.Order)
    .ToList();

// 2. Generate the Questions Header Row
var questionHeader = "Questions," + string.Join(",", questions.Select(q => $"\"{EscapeCsv(q.Text)}\""));
csv.AppendLine(questionHeader);

// 3. Generate the Answers Rows (one for each interview session)
int sessionIndex = 1;
foreach (var session in sessions)
{
    var answers = new List();
    foreach (var q in questions)
    {
        // Safely align the response to the correct question column, defaulting to empty if missing
        var response = session.Responses.FirstOrDefault(r => r.QuestionId == q.Id);
        answers.Add($"\"{EscapeCsv(response?.AnswerText ?? string.Empty)}\"");
    }

    var answerRow = $"Answer{sessionIndex}," + string.Join(",", answers);
    csv.AppendLine(answerRow);
    sessionIndex++;
}

Because LLM-generated transcriptions and user answers frequently contain commas, quotation marks, and line breaks, writing raw text to a CSV can break the file's structure. The export logic ensures all cells are enclosed in double quotes and uses a dedicated sanitisation helper to escape internal quotes, ensuring data integrity upon import.

// Helper method to handle internal quotes in strings to prevent CSV layout corruption
private string EscapeCsv(string? text)
{
    if (string.IsNullOrEmpty(text)) return string.Empty;
    
    // RFC 4180 standard: internal double-quotes must be escaped by doubling them
    return text.Replace("\"", "\"\"");
}

Saving Interview Responses (Internal API Flow)

The interview response pipeline is handled through an internal HTTP endpoint in ResponseAPIService. This local API pattern allows the Python/Llamafile orchestration flow to submit data asynchronously while the .NET side validates and persists each response.

Incoming payloads are mapped to the active ResponseSession, and answer text is dynamically resolved based on question type (for example, MCQ option text vs open-ended text). Completion state is tracked with _receivedResponseCount against _expectedQuestionCount before marking the session complete.

// Look up the exact question configuration

HeadTTS

The avatar generation is implemented by integrating an open-source browser-based 3D avatar rendering with an embedded Text-To-Speech (Kokoro TTS) and lipsync solution that takes in text input, HeadTTS, inside the AvatarPage using a WebView2 control. When the page initialises, a lightweight local web server is started to serve the HeadTTS assets. The WebView navigates to a dynamically constructed URL that includes avatar and voice parameters. This allows the application to control avatar configuration without modifying the frontend code directly. The avatar is loaded in the AvatarPage.

// Start local web server

{

    _webServer.Start();
}

AvatarWebView.CoreWebView2.Navigate(GetHeadTTSUrl());

GetHeadTTSUrl() injects query parameters such as avatar models, voice, language, and whether to use WASM (CPU) or WebGPU (GPU) for the TTS and lipsync model. The shared method from LlamafileProcessService, GetGPUInfo(), also helps here facillitate the choice between WASM and WebGPU based on system specifications.

private string GetHeadTTSUrl()
{
    var (gpuName, gpuMem) = GetGpuInfo();
    bool useWasm = true;

    if (gpuMem > 6144 && (gpuName.Contains("NVIDIA", StringComparison.OrdinalIgnoreCase) 
                        || gpuName.Contains("AMD", StringComparison.OrdinalIgnoreCase)))
    {
        useWasm = false; // Run on current logic (local inference/non-wasm)
    }

    string url = $"http://127.0.0.1:5501/index.html?avatar={_selectedAvatar}";
    if (!string.IsNullOrEmpty(_selectedVoice))
    {
        url += $"&voice={_selectedVoice}";
    }

    if (useWasm)
    {
        url += "&wasm=true";
    }

    return url;
}

Conversation Streaming

Communication between the backend Python agent and the avatar occurs through a WebSocket bridge for real-time streaming of speech content. The Python server maintains connected browser clients and pushes messages using:

await stream_message("speech", speech_line)

where the function stream_message() manages the connected client using asyncio and send messages through the Websockets channel:

async def stream_message(message_type, content):
    if connected_clients:
        message = json.dumps({
            "type": message_type,
            "content": content
        })

        await asyncio.gather(
            *[client.send(message) for client in connected_clients],
            return_exceptions=True
        )

These messages are received in the browser and passed into the HeadTTS pipeline:

function connectWebSocket() {
    ws = new WebSocket('ws://localhost:8883')

    // Connect to WebSockets
    // ...

    ws.onmessage = (event) => {
        const message = JSON.parse(event.data);

        if (message.type === 'speech') {
        if (!isPersonReady) {
            pendingSpeech.push(message.content);
            return;
        }

        synthesizeSpeech(message.content);
        }
    };

    // Manage WebSocket errors
    // ...

    // Close WebSocket connection
    // ...

}

After synthesizeSpeech(message.content), HeadTTS will produce the speech and animate the 3D avatar accordingly. This design removes the conversational logic from the visual layer, where the Python orchestrator layer handles interview flow, while HeadTTS handles the rendering and playback. Additionally, a buffering mechanism pendingSpeech ensures that speech is queued until the avatar and TTS engine are fully initialized, in case of avatar model or voice change mid-interview.

Overall, the implementation uses HeadTTS as the main rendering engine with real time communication via WebSockets to allow sub real-time (3X real-time) inferencing for both the Text-To-Speech and 3D avatar render components.

Speech Recognition

The multilingual speech recognition implementation in the AvatarPage is built around the Windows SpeechRecognizer API, which enables dynamic language selection. During initialisation, the system retrieves supported languages on the user's machine and binds them to a ComboBox, allowing the user to select their preferred speech recognition language from the frontend. This selection is persisted using the LocalSettingsService and restored on startup, ensuring consistency across sessions. The selected language is then stored in _selectedLanguage and used when constructing the recogniser instance, ensuring that speech is interpreted in the correct language from the get go rather than relying on post-processed translation. 

var languages = SpeechRecognizer.SupportedTopicLanguages;
LanguageComboBox.ItemsSource = languages;

_speechRecognizer = _selectedLanguage != null
    ? new SpeechRecognizer(_selectedLanguage)
    : new SpeechRecognizer();

The recognition pipeline is designed for interaction through continuous and incremental updates. The HypothesisGenerated event provides partial speech results, allowing the UI to update live as the user speaks, while the ResultGenerated event appends finalised segments into a cumulative transcript. A silence detection mechanism using a DispatcherTimer detects pauses and optionally triggers the auto-send feature to create a more natural conversational flow. This is designed to mimic human dialogue by allowing users to speak freely without needing to manually segment their input. 

_speechRecognizer.HypothesisGenerated += (s, args) =>
{
    var currentText = args.Hypothesis.Text;
    UserInput.Text = string.IsNullOrWhiteSpace(_finalizedSpeech) 
        ? currentText 
        : $"{_finalizedSpeech} {currentText}";
};

_speechRecognizer.ContinuousRecognitionSession.ResultGenerated += (s, args) =>
{
    if (args.Result.Status == SpeechRecognitionResultStatus.Success)
    {
        _finalizedSpeech += " " + args.Result.Text;
        UserInput.Text = _finalizedSpeech;
    }
};

Self-Contained Deployment

The .NET build system was used to generate a bundled version of our WinUI 3 code for Windows-based systems using the dotnet publish with some necessary properties as specified in PACKAGING_GUIDE.md. Although standard MSIX packaging is available out-of-the-box for Windows App SDK products, the nature of MSIX installers can create challenges and file size restrictions when executing our external bundled background processes, especially the standalone LLM .llamafile executable. Therefore, we decided to use a self-contained deployment approach targeting the win-x64 architecture, also aligning with our client request. The final executable and its dependencies are aggregated in the publish/ folder located **\AvatarForms\AvatarFormsApp\AvatarFormsApp\bin\Release\net10.0-windows10.0.19041.0\win-x64.
